# voidforge-core

The engine: world state, the per-planet solver, commands, domain events and views. It is a pure, single-threaded state machine with three entry points, `advance_to(t)`, `apply(command, t)` and `view(query, t)`, and each call returns the domain events it produced.

Library. P1.1 delivered `quantity` ([D-018](../../docs/decision-log.md#d-018-quantities-and-crossing-times)). P1.2 delivered `rules`: the typed specs and `Rules::validate`, which holds the rules invariants every caller relies on ([D-020](../../docs/decision-log.md#d-020-rules-data-files-and-ids)). P1.3 delivered `state`: `World` and every entity in ID-ordered maps, the checked ID counter, the event queue's data shape, serde, and `World::check_links`, which runs whenever a world is deserialized ([D-022](../../docs/decision-log.md#d-022-state-model-ids-and-test-builders)). P1.4 delivered the event loop in `state::engine`: `World::advance_to`, the `Steps` seam and `advance_with`, `schedule_planet` and `schedule_fleet` as the only way into the now private queue, the shared `entry_status` predicate, and the poisoned flag ([D-023](../../docs/decision-log.md#d-023-event-queue-advance_to-and-the-step-seam)). P1.6 delivered `solver`: the flows and their even split, labels (`planet_flows`), `World::solve_planet`, and `Solver`, the production steps that `advance_to(t, &Rules)` runs. ([D-025](../../docs/decision-log.md#d-025-per-planet-solver-part-1-its-seam-and-the-rules-it-reads)). P1.7 delivered transitions: constructions completing, ships completing with the Shipyard queue, demolitions ending, several at once in ID order, the loop guard, the three domain events and an atomic standalone solve ([D-026](../../docs/decision-log.md#d-026-per-planet-solver-part-2-transitions-their-order-events-and-the-loop-guard)). P1.8 delivered `fleet`: derived speed, capacity, distance and travel time, the engine-side `World::send_fleet` and `World::recall_fleet`, and the arrival and return steps `Solver` runs, with every mission outcome, the same-moment tie by fleet ID and their domain events ([D-027](../../docs/decision-log.md#d-027-fleets-derived-values-send-and-recall-arrivals-the-tie-and-their-events)). P1.9 delivered `command`: `World::apply` with Join game and the five planet and Shipyard commands, validated in a fixed order against the state at t, rejected with stable reason codes, applied atomically and re-solved ([D-028](../../docs/decision-log.md#d-028-commands-part-1-apply-join-game-the-planet-and-shipyard-commands-and-their-reason-codes)). P1.10 delivered the five fleet commands (`command/fleet.rs`): Assemble, Send, Recall, Disband and Trigger unload through `apply`, on D-027's mechanics and D-028's check order, with 18 more reason codes ([D-029](../../docs/decision-log.md#d-029-commands-part-2-the-five-fleet-commands-and-their-reason-codes)). P1.11 delivered `view`: `World::view` (the four queries with `valid_until`, exact `eta` and D-025 labels; fleets for their owner only) and `World::score` ([D-030](../../docs/decision-log.md#d-030-views-and-score); a building being demolished counts nothing, [D-039](../../docs/decision-log.md#d-039-a-building-being-demolished-stops-scoring-when-demolition-begins)). The layering in [Project layering](../../docs/Voidforge%20Technical%20Plan.md#project-layering) is the authority, and the [root AGENTS.md](../../AGENTS.md) covers repository-wide rules.

## Allowed dependencies

- Workspace: None. No workspace crate may be a dependency of the core.
- External at runtime, per the [Tech stack](../../docs/Voidforge%20Technical%20Plan.md#tech-stack): serde and thiserror only.
- Dev-dependencies, for tests only and never linked into the library: proptest and serde_json ([D-019](../../docs/decision-log.md#d-019-test-only-dev-dependencies-in-the-core)). Not testkit: core tests build their worlds by hand, so the core keeps no workspace dependency.
- Never: Anything else, including tokio, tracing and uuid. The core must not depend on the shell.
- Every new dependency needs a [decision log](../../docs/decision-log.md) entry, and its version goes in the [version table](../../docs/versions.md).

## Invariants

- No I/O, no clock reads, no threads, no random numbers ([Engine core](../../docs/Voidforge%20Architectural%20Design.md#engine-core)). Game time is a signed 64-bit count of milliseconds since the universe epoch, passed in by the caller ([Time model](../../docs/Voidforge%20Architectural%20Design.md#time-model)).
- Checked arithmetic: every integer operator is `checked_*` (with a typed error where input or state can reach overflow) or `strict_*` (only where a bound is proven, argued in a D-032 comment); `clippy::arithmetic_side_effects` is forbidden here ([D-032](../../docs/decision-log.md#d-032-checked-arithmetic-in-the-core-rules-and-worldgen)).
- Integers only: 64-bit storage, 128-bit intermediates, masses in grams, rates in grams per hour. No float types ([State model](../../docs/Voidforge%20Architectural%20Design.md#state-model)).
- Every collection iterates in ID order. Entities refer to each other by integer ID, never by pointer.
- New entities take `World.next_id`. Player UUIDs and other external keys arrive in commands; the core never generates them.
- One rounding rule: values round down with a carried remainder (floor division, non-negative remainder, never Rust's truncating `/`). A crossing is the first millisecond at which that read reaches the boundary; falling crossings are not the mirror of rising ones. A crossing quantity snaps to its boundary with its remainder reset to 0 ([Rounding formulas](../../docs/Voidforge%20Architectural%20Design.md#rounding-formulas)). `quantity::Quantity` implements this; every result outside 64 bits is a `QuantityError`, never wrapped or saturated.
- Total order: the queue is ordered by (time, kind rank, entity ID). At one instant, `PlanetChange` entries run by planet ID, then fleet entries by fleet ID, then commands by sequence number. A step never schedules work at its own instant ([Engine core](../../docs/Voidforge%20Architectural%20Design.md#engine-core)). Scheduling goes only through `schedule_planet` and `schedule_fleet`, which bump the version and reject a time not after now. Per-kind work plugs in as `Steps`, never as a second loop. An error from an advance, other than going back in time, poisons the world, which must then be discarded (D-023).
- `view` never writes; checkpoints happen only on events and commands.
- Another player's fleet or ship is unknown: it fails the existence check itself (`unknown_fleet`, `unknown_ship`), so at every check a foreign one is indistinguishable from one that doesn't exist. `not_owner` is only ever about a planet ([D-049](../../docs/decision-log.md#d-049-routes), amending D-028).
- `view_for(query, viewer, …)` is `view` as a player may see it: a planet's roster lists only the viewer's ships, and `valid_until` counts only the viewer's own fleets and the entity's own events. Staleness is still judged by the true validity, which counts every fleet, so the projection never crosses an event ([D-049](../../docs/decision-log.md#d-049-routes)).
- `World::free_homeworld` is public and read-only: Join game's check calls it, and the server's accounts path reads it from the read model to answer a full universe without appending a record, so the two cannot drift ([D-047](../../docs/decision-log.md#d-047-accounts-principal-to-player-and-join-game-exactly-once)).
- A command is validated against the state at its stamped time and applied atomically, or rejected with a reason code and no change ([Commands](../../docs/Voidforge%20Architectural%20Design.md#commands)).
- A next event that is not strictly after t, or too many transitions at one instant, stops the engine with an error. That is a bug, not a game state ([Next event](../../docs/Voidforge%20Architectural%20Design.md#next-event)).
- Only `voidforge-host` changes the live `World`. Two offline callers also drive `advance_to` and `apply`, never against live state: `voidforge-replay`, which rebuilds a world from a snapshot and the log, and tests ([Project layering](../../docs/Voidforge%20Technical%20Plan.md#project-layering)).
- The core does no instrumentation; it returns step statistics as plain data.
- The determinism rules apply here: no clocks, hash-ordered collections, threads, locks, system randomness, UUID generation or float arithmetic ([P0.4](../../docs/Voidforge%20Technical%20Plan.md#phase-0-foundations), [Determinism rules](../../docs/Voidforge%20Architectural%20Design.md#determinism-rules)). This crate's `clippy.toml` lists the banned paths, and `lib.rs` forbids the lints they feed, so no item can opt out. `tests/guardrails/run_fixtures.py` proves every ban here ([D-010](../../docs/decision-log.md#d-010-determinism-bans-in-core-rules-and-worldgen)). To ban another item, add it to all three identical `clippy.toml` files (core, rules, worldgen) and to a fixture. `tests/guardrails/check_no_floats.py` also rejects any `f32` or `f64` in this crate's compiled library, including floats no clippy ban can see ([D-013](../../docs/decision-log.md#d-013-type-aware-float-check)).

## Tests

```sh
cargo build -p voidforge-core
cargo clippy -p voidforge-core --all-targets -- -D warnings
cargo nextest run -p voidforge-core
```

P1.1's quantity tests compare reads, checkpoints and crossings on generated cases against an independent millisecond-stepping reference, plus named boundary and error cases (`src/quantity/tests.rs`; proptest runs with a fixed seed). P1.4's loop tests (`src/state/engine/tests.rs`) drive `advance_with` with probe steps on the hand-built sample world. P1.6's solver (`solver.rs`, [D-025](../../docs/decision-log.md#d-025-per-planet-solver-part-1-its-seam-and-the-rules-it-reads)) has its even-split unit tests in `src/solver/tests.rs`; its named tests per Technical Plan bullet run on Rules v0 worlds in testkit's `tests/solver.rs`, because core cannot read rules files. P1.5's determinism suite lives in testkit (`just determinism`, [D-024](../../docs/decision-log.md#d-024-determinism-suite-canonical-bytes-and-the-two-process-run)); every core change must keep it green, and a new step, command or view joins it as the testkit guide says. P1.8's distance and travel-time arithmetic is checked in `src/fleet/tests.rs` against the integer-root and first-covering-millisecond definitions; its named tests run on Rules v0 worlds in testkit's `tests/fleets.rs`. P1.9's command tests, one per accept and reject rule, run on Rules v0 worlds in testkit's `tests/commands.rs`. P1.10's fleet-command tests, one per accept and reject rule, are in testkit's `tests/fleet_commands.rs`. P1.11's view and score tests, including the done-when property (view at t = view after `advance_to(t)`), are in testkit's `tests/views.rs` ([Phase 1](../../docs/Voidforge%20Technical%20Plan.md#phase-1-core-engine), [Testing strategy](../../docs/Voidforge%20Architectural%20Design.md#testing-strategy)).
