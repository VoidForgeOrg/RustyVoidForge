# voidforge-server

The game API process. It checks tokens, maps accounts to players, runs the routes and the leaderboard job, and has the universe bootstrap subcommand. It serves `/openapi.json` on localhost:8080 locally.

Binary. P2.9 added its first subcommand, `seed`, the universe bootstrap ([D-043](../../docs/decision-log.md#d-043-the-universe-bootstrap-the-world-size-cap-and-just-seed)). It generates a universe and writes snapshot seq 0 into an empty database, and never overwrites one. Like `serve`, it takes its database only from `--database-url` or `VOIDFORGE_DATABASE_URL`, never `DATABASE_URL`, and it refuses a database that isn't empty before migrating anything ([D-055](../../docs/decision-log.md#d-055-phase-3-gate-repair)). `just seed` targets only `voidforge_dev`, never `voidforge`. Exit codes: 0 seeded, 2 usage, 3 refused, 4 input or database error, 5 telemetry. `seed` also records the universe's epoch (`--epoch-unix-ms`, default now, inside 1970 to 2100). P3.4s added `serve` (`voidforge_server::serve`, [D-050](../../docs/decision-log.md#d-050-serve-the-durable-epoch-and-the-travel-horizon)): it refuses a database without a universe before migrating anything, reads the recorded epoch (never a flag or the clock), recovers the host from Postgres, runs `refresh_forever` beside the router, prints one `ready:` line, and on SIGINT or SIGTERM drains for `--drain-secs`, stops the host, and exits 0 only when the final snapshot is at the log head. Exit codes: 0 clean, 2 usage, 3 refused, 4 input or database error, 5 telemetry, 6 unclean (a second signal, a drain timeout, or the host stopping on its own). The layering in [Project layering](../../docs/Voidforge%20Technical%20Plan.md#project-layering) is the authority, and the [root AGENTS.md](../../AGENTS.md) covers repository-wide rules.

## Allowed dependencies

- Workspace: `voidforge-host`, `voidforge-store`, `voidforge-rules`, `voidforge-worldgen`, `voidforge-api-types`, `voidforge-telemetry`.
- External, per the [Tech stack](../../docs/Voidforge%20Technical%20Plan.md#tech-stack): The API stack from the Tech stack: tokio, axum, tower-http, jsonwebtoken (on the aws-lc-rs backend), reqwest (to fetch dex's signing keys; no TLS until P5), uuid (v7), utoipa, tower_governor, clap and anyhow (D-046).
- Never: voidforge-core directly. Engine state changes only through the host, and the server names core types (`Command`, `Action`, `Rejection`, `PlayerId`, `World`) through the host's re-exports (D-047). (Its tests take core as a dev-dependency only: the database-stage tests build a Join game command for the host, and `tests/api_codes.rs` checks the API's game codes against the core's reason codes, D-045.)
- Every new dependency needs a [decision log](../../docs/decision-log.md) entry, and its version goes in the [version table](../../docs/versions.md).

## Invariants

- Telemetry: `main` calls `voidforge_telemetry::init` once, first, and `Telemetry::shutdown` before exit, reporting a failed shutdown with a non-zero exit ([D-016](../../docs/decision-log.md#d-016-telemetry-bootstrap)). It never configures its own exporter or subscriber.
- Nothing in the engine knows about auth. The API turns a dex ID token into a player UUID before any command reaches the host, and never sees a password ([Auth](../../docs/Voidforge%20Technical%20Plan.md#auth)).
- `serve` takes its database only from `--database-url` or `VOIDFORGE_DATABASE_URL`, never `DATABASE_URL` (a stray one could point it at the owner's database), and never prints it. `just serve` targets only `voidforge_dev`. Nothing in `serve` keeps a `HostHandle` past the drain: a surviving handle would keep the host from stopping (its join is bounded at 10 s, then exit 6). One control runtime owns the single signal stream and selects every shutdown step against it, the final snapshot check included (bounded at 5 s), so a second signal is never lost between phases. A session advisory lock (`voidforge_store::lock_universe`) makes a second `serve` on the same universe refuse with exit 3 before recovery or bind. Compose runs the binary itself, never `just` (D-050).
- Tokens are checked against dex's cached signing keys, issuer, the audience allowlist and expiry. Anything else gets 401 (`voidforge_server::auth`, D-046). The header is checked before any key state; RS256 only. When dex's keys can't be loaded, a well-formed token gets 503 with Retry-After, never an accept. No token text in bodies or logs.
- All writes go through `POST /commands` with a required `Idempotency-Key` header. The player comes from the token, never from the body.
- Status mapping: 200 accepted, 400, 401, 422 for a rule violation with its reason code, 503 with Retry-After when the inbox is full, and 429 `rate_limited` with Retry-After for the rate limit.
- An `accounts` row maps issuer and subject to a player UUIDv7. The first authenticated call creates it and issues Join game, exactly once (`voidforge_server::accounts`, D-047):
  - The row comes first, then the join. Each call looks the row up (inserting only when missing), then joins if the read model does not show the player. A crash between the two is repaired by that user's next call.
  - The join has no idempotency key: D-037 would keep a rejection under it permanently. The core's `already_joined` refusal, under the single writer, is the deduplicator, and an `already_joined` receipt counts as joined.
  - A refused join is 422 with the core's code (`no_free_homeworld`), and the row stays. A full universe is answered from the read model, without appending a record. A refused account gets that 422 on every route that takes a player, reads included: there is no spectator mode.
  - The subject is personal data. It is never logged at any level, and never appears in an error body, a panic message or a `Debug` output; the player UUID is the public identity.
- Rate limits (`voidforge_server::limit`, [D-054](../../docs/decision-log.md#d-054-rate-limits-per-principal-gcra-read-and-write-budgets)): GCRA per principal, with a read budget (every method but `POST`) and a write budget (`POST`), chosen by the method, never the path. The defaults are reads 10 a second with bursts of 40 and writes 2 a second with bursts of 10, set by `serve`'s `--read-rate`, `--read-burst`, `--write-rate` and `--write-burst`. The check sits inside the `Player` extractor, after the token and before the account, so a 429 never makes an account, joins, reaches the host or consumes an idempotency key; a refused account's 422s count. 401s, the 503 while keys load and `/openapi.json` are never counted. A refusal changes nothing. The key is a keyed hash of the principal, never the subject, and idle entries are swept, so memory stays bounded. A route that acts as a player must take `Player`, or it bypasses the limit (the route-table test catches it).
- The leaderboard is rebuilt every 60 seconds (`--leaderboard-secs`) from the read model and served with its `as_of` (`voidforge_server::leaderboard`, [D-051](../../docs/decision-log.md#d-051-the-leaderboard)). Each player's score comes through the route's own `view_for(Query::Player)` call at the build's one `t`, so the board equals `/players/me` at the same time. A failed build keeps the previous board; before the first, the route is 503 with Retry-After 1. The job runs on `serve`'s server runtime, so the shutdown drops it with its handle.

## Tests

```sh
cargo build -p voidforge-server
cargo clippy -p voidforge-server --all-targets -- -D warnings
cargo nextest run -p voidforge-server
```

- `tests/cli.rs` covers the cap, the exit codes, and that the URL is never printed.
- `tests/postgres.rs` (database stage) covers the pinned seed hash on fresh databases, the refusal on a non-empty or accounts-only database, the refusal of a database with other tables or only partly migrated with the schema left unchanged (D-055), and recovery after seed.
- `tests/auth.rs` covers the token checks over real HTTP, against a local dex stand-in with keys generated at run time (D-046): every refusal's code and headers, rotation, the refresh floor, single-flight, dex down, stale keys, and the configuration bounds.
- `tests/dex.rs` (`just dex-test`, by hand) checks the real dex. It needs `DEX_CONFIG=config.ci.yaml just up` for the password-grant token.
- `tests/api_codes.rs` checks that the API's 422 codes are the core's reason codes (D-045).
- `tests/routes.rs` (database stage) drives every route over HTTP through the real router, host, `Players` and Postgres: each 200 and error body as an insta snapshot, the privacy rule, the viewer rules, near's checks and cap, stale reads, 401 and 503 on every authenticated route, `no_free_homeworld` on every route, and route/document parity, with every status checked against the document (D-049). P3.8 adds the rate limits on a stepped clock: every route in the table limited but `/openapi.json`, players independent, a limited command appending nothing and its key later getting its real outcome, a limited principal making no account, refused accounts counted and 401s not, and the budget chosen by the method (D-054).
- `tests/accounts.rs` (database stage) drives the account path through the real host and Postgres: one row and one homeworld per principal across repeats, concurrency, a full universe, a stopped or busy host, restarts and four kill points, every error's answer, and the subject never logged at TRACE, sqlx included (D-047). `tests/postgres.rs` also covers seed's refusal of an accounts-only database, under a race.
- `tests/serve.rs` (database stage) runs the real binary over a seeded `_sqlx_test_*` database and a dex stand-in, stopped with real signals: SIGINT and SIGTERM restarts (the same epoch, recovery from the shutdown snapshot, game time continuing), the refusals (an empty database left without tables, no recorded epoch, epochs out of the window at seed and at serve), dex down at startup, a request in flight at shutdown (made certain by a held `LOCK TABLE log_records`), a request held past the drain, a second signal, SIGKILL, and the host dying (a raising trigger). Every wait is bounded, and a failing test kills its child (D-050).

P2.9: on an empty database, the bootstrap always yields the same state hash. P3.2 to P3.5 and P3.8: token, account, route (insta contract snapshots), leaderboard and rate-limit tests.
